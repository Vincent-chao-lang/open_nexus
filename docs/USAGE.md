> **定位：面向老旧 Python 项目的安全自动化重构框架。** 通过异构多 Agent 协同和"地图→扫描→重构"三步流程，让开发者安全、可控地完成遗留代码的现代化改造。

## 1. 安装与配置

### 1.1 环境要求

- Python 3.10+
- Git（用于安全回滚）

### 1.2 安装

```bash
cd open_nexus
pip install -r requirements.txt
```

依赖包：`litellm`、`pydantic`、`pyyaml`、`python-dotenv`

### 1.3 配置 API Key

```bash
cp config/.env.example config/.env
```

编辑 `config/.env`，填入至少**两家**不同厂商的模型 Key：

```bash
ANTHROPIC_API_KEY=sk-ant-xxx    # 用于 Planner（架构规划）
OPENAI_API_KEY=sk-xxx           # 用于 Reviewer（异构审计）
DEEPSEEK_API_KEY=sk-xxx         # 用于 Executor（代码生成，性价比高）
```

**为什么需要两家？** 框架的核心设计是"异构对抗"——Executor 和 Reviewer 必须使用不同厂商的模型，才能利用它们"错得不一样"的特性互相纠错。如果只有一家厂商的 Key，异构审计将退化为同模型自查，效果大打折扣。

> 如果使用中转 API 或自定义网关，可以在 `.env` 中追加 `_BASE_URL` 配置。

### 1.4 配置目标项目路径

编辑 `config/nexus_config.yaml` 中的 `safety.git_repo_path`，或在命令行通过 `-p` 参数指定：

```yaml
safety:
  git_repo_path: "/Users/you/your-legacy-project"
```

后面所有命令中的相对路径（如 `src/engine/`）都相对于这个目录。

## 2. 核心概念：你的角色变了

使用 Open-Nexus 时，你的角色从"写代码的人"变成了"**总架构师**"。你的工作不再是逐行修改代码，而是：

1. **定义边界** — 告诉框架这次手术的范围（哪些文件？改什么？）
2. **确认契约** — 审核 AI 推断的架构规则是否正确
3. **处理干预** — 当多个 Agent 争吵不休或预算超支时，你来拍板

框架的工作流对应三个阶段：

```
地图（理解架构） ──→ 扫描（看清问题） ──→ 重构（精准动刀） ──→ 验证 ──→ 下一轮
  --map            --scan              -t "目标" 文件
```

**先地图，再扫描，最后重构。** 不要跳过前两步直接动刀——那相当于不看地图不做体检就做手术。

## 3. 第一步：理解项目全貌（地图模式）

### 3.1 为什么第一步是地图

面对一个陌生项目，你首先需要回答：

- 这个项目到底是干什么的？
- 数据从入口进来，经过哪些模块，最终落到哪里？
- 哪些是核心业务逻辑，哪些是工具辅助代码？
- 新人应该按什么顺序阅读代码？

**地图模式就是为回答这些问题而生的。** 它是整个重构流程的第一步——先用一次 AI 调用生成结构化的架构导航文档，让你在动刀之前心里有数。

### 3.2 基本用法

```bash
# 全项目地图
python main.py --map

# 指定关注范围
python main.py --map --scope src/engine/ src/api/

# JSON 格式（方便集成到其他工具）
python main.py --map -f json

# 指定项目路径
python main.py --map -p ~/your-project
```

### 3.3 地图包含什么

地图输出四个部分：

**1. 项目概览**
从模块命名和依赖关系推断项目用途。AI 会综合所有文件名、类名、函数名和依赖边，给出一个合理的项目定位判断。

**2. 分层架构说明**
文件按"被依赖数"和"出度数"自动分为 4 层：

| 层级 | in-degree | out-degree | 典型模块 |
|------|-----------|------------|---------|
| 入口层 | 高 | 低 | controllers, routes, CLI |
| 核心逻辑层 | 高 | 高 | services, engines, managers |
| 数据/基础设施层 | 低 | 高 | models, db connections, base classes |
| 独立模块 | 低 | 低 | standalone utilities, config |

- **in-degree**：有多少个其他文件依赖我（被依赖数）
- **out-degree**：我依赖了多少个其他文件（依赖数）

分层基于中位数分割，所以在大型项目（>20 文件）中比较准确。

**3. 模块逐个导读**
每个文件的一句话用途说明和关键接口列表。

**4. 建议阅读路径**
新人应该按什么顺序阅读代码（3-5 步），从入口到核心到基础设施逐层深入。

### 3.4 输出示例

```
============================================================
  Open-Nexus 项目地图
  项目: legacy-backend
  文件总数: 42
  问题: 87 个 (5 Critical, 52 Warning, 30 Info)
============================================================

## 分层架构（本地分析）

### 入口层 (3 个文件)
被依赖较多但依赖较少——项目对外的接口层，类似 controllers/routes
  - src/api/routes.py
  - src/cli.py
  - src/api/middleware.py

### 核心逻辑层 (12 个文件)
被依赖多且依赖也多——业务逻辑枢纽，类似 services/engines
  - src/engine/runner.py
  - src/engine/context.py
  - src/auth/manager.py
  ...

============================================================
  AI 架构分析
============================================================
### 1. 项目概览
这是一个 FastAPI 后端服务，包含用户认证、任务引擎和数据库持久化三层...
### 2. 分层架构说明
...
### 3. 模块逐个导读
...
### 4. 建议阅读路径
Step 1: src/api/routes.py — 从 HTTP 入口理解项目对外提供什么
Step 2: src/engine/runner.py — 理解核心业务调度逻辑
Step 3: src/db/connection.py — 理解数据如何存储
Step 4: src/auth/manager.py — 理解认证流程
```

### 3.5 地图模式消耗

- 一次 `--map` 调用消耗约 1 次 Planner 调用
- 输入 Token：依赖图 + 函数签名（约 2000-5000 tokens，取决于文件数）
- 输出 Token：架构概述（约 1000-2000 tokens）
- 费用：约 $0.02-$0.05（使用 Claude 3.5 Sonnet）

## 4. 第二步：项目体检（扫描模式）

### 4.1 基本用法

```bash
python main.py --scan -p ~/your-project
```

这会扫描整个项目的所有 `.py` 文件，输出：

- 文件总数和问题总数
- 按严重程度分级的问题清单
- 依赖关系概览
- **重构路线图**（告诉你先改什么、再改什么）

### 4.2 扫描模式不消耗 Token

扫描完全在本地完成——AST 解析、行数统计、嵌套深度计算——不调用任何 API。你可以反复扫描，随时了解项目状态。

### 4.3 JSON 输出

```bash
python main.py --scan -p ~/your-project -f json
```

JSON 格式方便集成到 CI 流程或喂给其他分析工具。

### 4.4 扫描检测什么

| 严重级别 | 检测项 | 阈值 | 示例 |
|---------|-------|------|------|
| **Critical** | 长函数 | > 80 行 | "强烈建议拆分为 3-5 个小函数" |
| **Critical** | 大类 | > 12 个方法 | "职责可能过重，建议按职责拆分" |
| **Warning** | 中等长度函数 | > 40 行 | "考虑提取子逻辑" |
| **Warning** | 参数过多 | > 5 个 | "考虑封装为数据类或配置对象" |
| **Warning** | 嵌套过深 | > 4 层 | "建议提取内层逻辑或使用提前返回" |
| **Warning** | IO 与业务逻辑混杂 | 关键词匹配 | "建议分离为纯函数 + IO 层" |
| **Warning** | 构造函数依赖过多 | > 5 个 | "考虑引入依赖注入容器" |
| **Info** | 缺少类型注解 | 函数 > 15 行 | "建议添加参数和返回值类型" |

### 4.5 与地图模式的区别

| 维度       | 扫描模式 `--scan`        | 地图模式 `--map`               |
| ---------- | ------------------------ | ------------------------------ |
| 目的       | 发现代码质量问题         | 理解项目架构和职责             |
| 分析方法   | 纯 AST 静态分析          | 本地分层 + AI 语义理解         |
| Token 消耗 | 0                        | ~1 次 Planner 调用             |
| 输出       | 问题清单 + 路线图        | 架构概览 + 模块导读 + 阅读路径 |
| 问题类型   | 长函数、大类、参数过多等 | 模块职责、数据流向、核心识别   |

**两者互补**：扫描让你知道"该修什么"，地图让你知道"改的是什么"。

## 5. 第三步：读懂体检报告

### 5.1 报告结构

扫描完成后你会看到这样一份报告：

```
============================================================
  Open-Nexus 项目体检报告
  项目: your-project
  文件总数: 42
============================================================

  发现问题: 87 个
    Critical: 5 个
    Warning:  52 个
    Info:     30 个

────────────────────────────────────────────────────────────
  [CRITICAL] 严重问题（建议优先处理）
────────────────────────────────────────────────────────────
  src/engine/runner.py:120  process_batch
    → 长函数 (145 行) — 强烈建议拆分为 3-5 个小函数
  ...

────────────────────────────────────────────────────────────
  [WARNING] 警告
────────────────────────────────────────────────────────────
  src/auth/manager.py:45  authenticate
    → 中等长度函数 (52 行) — 考虑提取子逻辑
  ...

============================================================
  重构路线图
============================================================

  Phase 1: 底层依赖 + 严重问题 — 最优先修复，影响面最大
  ──────────────────────────────────────────────────
    [CRITICAL] src/db/connection.py (被 15 个模块依赖)
    [CRITICAL] src/engine/runner.py (被 8 个模块依赖)

  Phase 2: 中等优先级 — 被依赖较少或问题较轻
  ──────────────────────────────────────────────────
    [WARNING] src/auth/manager.py (被 3 个模块依赖)
    ...

  Phase 3: 上层入口/叶子模块 — 最后处理，避免接口变更影响下游
  ──────────────────────────────────────────────────
    [WARNING] src/api/routes.py (被 0 个模块依赖)
    ...
```

### 5.2 怎么读路线图

路线图按两个维度排序：

1. **被依赖数**：一个文件被多少个其他模块引用。被依赖越多，说明它是"地基"，改动它影响面最大——所以要**最先修**。
2. **严重程度**：Critical 优先于 Warning。

所以 Phase 1 里的是"被很多人依赖、且自身有严重问题"的文件——修好它们，收益最大。Phase 3 里的是"没人依赖、问题也不严重"的叶子节点——影响面最小，可以最后改。

### 5.3 判断建议是否合理

扫描器基于静态阈值，**不是所有建议都需要采纳**：

- `run_pipeline`（123 行）被标为 Critical 长函数 → **合理**，确实应该拆分
- `_scan_file` 被标为"IO 与业务逻辑混杂" → **可能误报**，因为 `ast.parse(open(...))` 被关键词匹配到了，但它本身就是做代码分析的，IO 是核心逻辑
- `parse_args`（59 行）被标为中等长度 → **可以忽略**，argparse 配置函数长一点是正常的

**你的判断始终是最终裁决。扫描器只提供建议，不替你决策。**

## 6. 第四步：制定重构计划

### 6.1 选择切入点

看完报告后，选出第一轮重构的目标。原则：

1. **从 Phase 1 开始**，挑 3-5 个关联最紧密的文件
2. **不要一次动太多** —— 超过 10 个文件，模型会失焦，成本会爆炸
3. **优先修"被依赖最多"的底层模块** —— 地基修好了，上层自然受益

### 6.2 明确重构目标

每个任务必须有一个清晰、具体的目标。目标决定了 Planner 如何分析、Executor 如何写代码、Reviewer 如何审计。

**好的目标描述：**
- "将 `UserManager` 类中的邮件发送逻辑提取为独立的 `EmailService`"
- "将 `process_batch` 函数从 145 行拆分为 4 个不超过 40 行的子函数"
- "给 `src/db/` 下的所有函数添加完整的类型注解"

**不好的目标描述：**

- "重构这个文件" —— 太模糊，各 Agent 理解不一致
- "让代码变好" —— 无法验证是否达成

### 6.3 示例计划

假设扫描报告显示：

```
Phase 1: src/db/connection.py (被 15 个模块依赖, Critical)
         src/models/base.py    (被 10 个模块依赖, Critical)
         src/engine/runner.py  (被 8 个模块依赖, Critical)
```

你的计划可以是：

```
第 1 轮: src/db/connection.py + src/models/base.py
         目标: "增加类型注解，拆分 connection.py 中的长函数"
         理由: 这两个是底层依赖，其他 15 个模块都依赖它们。先修好地基。

第 2 轮: src/engine/runner.py
         目标: "拆分 145 行的 process_batch 函数，提取数据处理管道"
         理由: 第 1 轮修好地基后，第 2 轮修引擎不会引发连锁错误。

第 3 轮: Phase 2 的 3-5 个文件
         ...
```

## 7. 第五步：执行重构（重构模式）

### 7.1 基本用法

```bash
python main.py -t "重构目标" <文件或目录> [-p 项目路径]
```

- `-t` / `--task`：**必填**，描述你希望对目标代码做什么
- 文件/目录：**必填**，支持单个文件、多个文件、目录、混合输入
- `-p` / `--project`：可选，覆盖配置文件中的项目路径

### 7.2 单文件重构

```bash
python main.py -t "拆分 UserManager，将邮件发送逻辑提取为独立的 EmailService" \
               src/legacy_code.py
```

### 7.3 多文件重构

```bash
python main.py -t "将同步 IO 改为 async/await" \
               src/auth/manager.py src/auth/session.py src/auth/token.py
```

### 7.4 目录重构

```bash
python main.py -t "为 src/engine/ 下所有函数添加类型注解" \
               src/engine/
```

目录会递归展开所有 `.py` 文件，自动跳过 `__pycache__`/`venv`/`.git` 等非代码目录。

### 7.5 观察运行过程

运行时会看到每个阶段的输出：


### 7.6 重构失败了怎么办

如果看到：

```
[Nexus] 重构未通过验证（状态: human_required）。
[Nexus] 总消耗: $0.8500
[Nexus] 已自动回滚。
```

说明 Reviewer 连续 3 次驳回了 Executor 的代码，或者预算超限。此时：

1. 代码已自动回滚到任务开始前的状态（Git reset）
2. 查看 Reviewer 的最后驳回原因：
   ```
   [Orchestrator] 最后 Reviewer 反馈：
   "Executor 将 send_email 改为 async 后，
    但没有 await 调用，导致邮件实际不会发送"
   ```
3. 根据反馈决定：手动修改后重新提交，还是追加约束后再跑一次

## 8. 第六步：验证与迭代

### 8.1 验证重构结果

重构完成后，务必：

1. **运行项目现有测试**：`pytest` 或项目的测试命令，确保没有引入回归错误
2. **检查生成的代码**：即使 Reviewer 给了 LGTM，也建议肉眼过一遍关键逻辑
3. **运行扫描确认改善**：
   ```bash
   python main.py --scan -p ~/your-project
   ```
   对比扫描前后的 Critical/Warning 数量，确认问题确实减少了

### 8.2 进入下一轮

第一轮重构提交后，回到扫描报告，选择 Phase 1 的下一个目标，继续下一轮。每轮结束后跑一次扫描，你能直观地看到项目健康度的提升。

## 9. 人工干预

以下情况需要你介入决策：

| 信号 | 含义 | 处理方式 |
|------|------|---------|
| `status: human_required` | 3 次迭代未通过评审，或预算超限 | 查看 Reviewer 反馈，决定手动修改还是追加约束后重跑 |
| 路线图建议不采纳 | 你判断某个 Critical 不需要改 | 跳过，直接选择下一个 Phase 1 目标 |
| Reviewer 和 Executor 反复互驳 | 该问题可能落入模型公约数盲区 | 不要继续烧 Token，直接人工裁决 |
| 成本累计接近预算上限 | 任务可能完成不了 | 调整 `budget_limit`，或将任务拆成更小的子任务 |

```yaml
  sqlite_path: "./data/logic_graph.db"   # 经验记忆存储位置
  decay_lambda_t: 0.05                   # 时间衰减系数（越小越慢衰减）
  decay_lambda_v: 0.3                    # 模型版本衰减系数（版本升级时大幅降权）
  confidence_threshold: 0.4              # 低于此分的记忆不再自动注入

  git_repo_path: "./"                    # 目标项目路径（会被 -p 覆盖）
```

### 9.1 模型替换

你可以用任何 LiteLLM 支持的模型：

```yaml
# 全部用 OpenAI
models:
  planner: "openai/gpt-4o"
  executor: "openai/gpt-4o-mini"    # 至少用不同型号
  reviewer: "openai/gpt-4o"

# 或本地模型
models:
  planner: "ollama/llama3.1:70b"
  executor: "ollama/deepseek-coder-v2"
  reviewer: "openai/gpt-4o"         # Reviewer 建议保留云端强模型
```

**重要**：Executor 和 Reviewer 必须是不同模型。否则异构对抗退化为同模型自查，盲区重合。

### 9.2 预算调整

根据项目规模调整：

| 场景 | 建议 budget_limit |
|------|------------------|
| 单文件，加类型注解 | $0.3 - $0.5 |
| 单文件，拆分长函数 | $0.5 - $1.0 |
| 3-5 个文件，架构级重构 | $2.0 - $5.0 |
| 10+ 文件，跨模块重构 | $5.0 - $10.0（建议拆为多次运行） |

## 11. 常见问题

### Q: 扫描报告说我有很多问题，该从哪里开始？

A: 看路线图的 Phase 1。那些文件同时满足"被很多模块依赖 + 有严重问题"，修好它们收益最大。不要试图一次修完所有问题——分批来。

### Q: 为什么不能直接把整个项目扔给模型重构？

A: 两个原因。一是上下文窗口有限，几十万行代码塞不进去；二是即使塞得进去，模型会"注意力失焦"，改了 A 忘了 B。框架的做法是分而治之：扫描出问题 → 按依赖排序 → 每次只重构 3-5 个关联文件。

### Q: 自动生成的测试可信吗？

A: **不可信。** 它只是 happy-path 骨架，确保基本调用不报错。边界条件、异常路径、Mock 外部依赖——这些你必须自己补充。把它看作"防止重构后连基本功能都跑不通"的最低保障，不是测试覆盖的终点。

### Q: Reviewer 给了 LGTM，我能直接合代码吗？

A: **不能。** LGTM 是概率性保障，不是确定性验证。尤其是涉及异步并发、多线程同步等复杂场景时，GPT-4o 和 Claude 的盲区可能重合。至少要做一次 Code Review + 运行完整测试套件。

### Q: 为什么扫描器说我的函数"混合 IO 和业务逻辑"，但我觉得没问题？

A: 扫描器的 IO 检测基于关键词匹配（`open(`、`requests.`、`execute(` 等），存在误报。如果你确定该函数的设计是合理的（比如它的职责就是做文件处理），忽略这条建议即可。扫描器提供数据，你来做判断。

### Q: 框架支持非 Python 项目吗？

A: 不支持。AST 分析、测试生成、依赖扫描都基于 Python 语法树。多语言支持需要大量额外工作。

### Q: 能同时跑多个重构任务吗？

A: 不建议。每个任务会操作 Git（checkpoint/commit/rollback），并发执行可能导致 Git 状态冲突。如果项目很大，应该串行执行，一个阶段完成后再开始下一个。
