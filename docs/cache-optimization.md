# DeepSeek 缓存命中率优化

> **目标**：通过固定前缀策略，将 DeepSeek（Executor）的 input token 缓存命中率从 ≈0% 提升到 50-80%，单次任务成本降低 70%+。

## 1. 背景：DeepSeek 缓存计价模型

DeepSeek V4 Pro 采用**前缀匹配缓存**：两次请求的 prompt 开头部分相同时，相同前缀的 token 自动命中缓存，价格降至 1/10。

| 缓存状态 | 价格（每 1M input tokens） |
|---------|:------------------------:|
| Cache Miss | $0.14 |
| Cache Hit | $0.014 |

**关键约束**：缓存匹配是字节级前缀匹配，prompt 开头的任何变化都会导致后续全部 token 无法命中。

## 2. 当前问题

Open-Nexus 的 `Orchestrator._call_model()` 中，每个阶段的 prompt 结构完全不同：

```
请求 1 (Planner):   "你现在是资深代码分析专家..." + 目标 + 邻居签名 + 历史
请求 2 (Planner):   "基于以下架构契约..." + 契约 + 目标 + 源码
请求 3 (Executor):  "实现以下重构目标..." + 契约 + 规划 + 反馈 + 源码
请求 4 (Reviewer):  "你作为最后一道逻辑防线..." + 契约 + 原代码 + 新代码
```

**每次请求的"角色指令"在最前面，各不相同 → 前缀无交集 → 缓存命中率 ≈ 0%。**

## 3. 优化方案：固定前缀模板

### 3.1 核心思路

将所有请求拆分为两部分：

```
┌─────────────────────────────────────┐
│  固定前缀（任务级不变）              │  ← DeepSeek 缓存命中区域
│  - 全局约束                         │
│  - 项目结构                         │
│  - 重构目标                         │
│  - 架构契约                         │
│  - 源码（首次迭代后不变）             │
│  - 历史经验                         │
├─────────────────────────────────────┤
│  变化部分（每次请求不同）            │  ← 实际计算区域
│  - 角色指令                         │
│  - 上轮反馈                         │
│  - 重构后代码（Reviewer 请求）       │
└─────────────────────────────────────┘
```

`Orchestrator._build_cache_prefix()` 在任务初始化时预计算固定前缀，后续所有 `_call_model()` 调用自动拼在最前面。

### 3.2 改造后的 Prompt 组装模式

```python
# 固定前缀（所有角色共享，同一任务内不变）
cache_prefix = f"""
# Open-Nexus 重构框架
## 全局约束
{config['global_constraints']}

## 当前任务
目标: {task_description}
目标文件: {target_files}

## 架构契约
{architecture_contract}

## 源码
{code_map}

---

"""

# 各阶段只追加角色指令（变化部分放最后）
planner_prompt = cache_prefix + "角色: Planner\n制定重构计划..."
executor_prompt = cache_prefix + "角色: Executor\n生成代码...\n上轮反馈: {feedback}"
reviewer_prompt = cache_prefix + "角色: Reviewer\n审计代码...\n重构后代码: {new_code}"
```

### 3.3 对源码变动的处理

源码是一开始就进入固定前缀，还是每轮迭代后才加入？

- **首次 Executor 调用**：源码是新的，整段计入 miss。但架构契约 + 项目结构 + 目标描述部分命中。
- **L1 语法失败重试**：源码、契约全在缓存，只有语法错误提示是新的 → 命中率 ~80%。
- **Reviewer 驳回重试**：源码、契约全在缓存，只有驳回原因是新的 → 命中率 ~60%。
- **Reviewer 调用**：源码、契约全在缓存，只有重构后代码是新的 → 命中率 ~50%。

## 4. 预期收益

### 4.1 单次任务 Executor 成本对比

假设：目标 3 文件，3000 行代码，8000 input tokens/次：

| 调用序号 | 场景 | 改造前 | 缓存命中 tokens | 改造后 | 节省 |
|:-------:|------|:------:|:------------:|:------:|:----:|
| 1 | 首次 Executor | $1.12 | ~3000 | $0.70 | 37% |
| 2 | L1 语法失败重试 | $1.12 | ~6500 | $0.29 | 74% |
| 3 | Reviewer 驳回重试 | $1.26 | ~7500 | $0.25 | 80% |
| 4 | 再次驳回重试 | $1.40 | ~8000 | $0.25 | 82% |
| **合计** | | **$4.90** | | **$1.49** | **70%** |

### 4.2 跨阶段效果

同一任务内 Planner→Executor→Reviewer 的固定前缀部分（合约 + 源码 + 目标）全部命中：

| 角色 | 模型 | 改造前/次 | 改造后/次 |
|------|------|:------:|:------:|
| Planner（第2次） | Claude | $0.06 | $0.06（非 DeepSeek，不适用）|
| Executor（每次） | DeepSeek | $1.12 | $0.30-$0.70 |
| Reviewer | GPT-4o | $0.40 | $0.40（非 DeepSeek，不适用）|

**DeepSeek 之外的模型不受益**，但 Executor 是调用次数最多的角色，占比 >60%。

## 7. 注意事项

1. **固定前缀不能太长**：超过 DeepSeek 缓存窗口会失效。建议控制在 20K tokens 以内。
2. **跨任务不共享**：不同重构任务的目标、文件、合约都不同，缓存不跨任务命中（除非未来引入项目级固定前缀）。
3. **Claude/GPT-4o 不适用**：它们的缓存机制不同（Claude 是 prompt caching API，GPT 是 automatic caching），需要单独适配。
4. **实际效果需实测**：缓存命中率取决于 DeepSeek 的具体实现细节，以上为理论估算。
